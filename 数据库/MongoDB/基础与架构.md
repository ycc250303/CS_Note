面试别只答「NoSQL、文档型、存 JSON」。要能说清：MySQL 在什么场景难受、文档怎么存、单机引擎怎么干活、十亿级怎么扩。

## 为什么还要 MongoDB

场景：十亿级游戏用户。字段一直加（装备、活动、是否拜师），还要多维查询，例如「没参加情人节活动的剑士」。

用 MySQL 能做，但会越来越难受：

* **预留列浪费空间**：活动字段越加越多，多数用户用不上，行模型里列定义在那，空值成本一直在
* **迭代要改表**：大表 `ALTER TABLE`、补索引，线上变更风险高
* **动态属性不顺手**：玩家档案更像可扩展的一整份文档，不是固定列

MongoDB 和 MySQL **不是替代，是互补**。看数据形态和访问模式。

| | MongoDB 更合适 | MySQL 更合适 |
| --- | --- | --- |
| 形态 | 字段常变、文档天然是一个整体（画像、玩家档案、订单快照） | 强结构、强约束 |
| 访问 | 少 JOIN、按文档读写 | 复杂 JOIN、分析 SQL 生态成熟 |
| 一致性 | 可接受文档级为主，4.0+ 才有多文档事务 | 强 ACID（账务、库存、交易流水） |
| 扩展 | 分片水平扩展更顺手 | 垂直扩展 + 分库分表 |

工业界常见混用：核心交易走 MySQL，画像/可扩展属性走 MongoDB，缓存 Redis，搜索/日志 ES。

## 是什么：文档数据库

开源、C++ 写的 **文档型 NoSQL**。面向文档、**无模式**建模，高负载下原生支持水平扩展和高可用。一句话：**数据结构更灵活的数据库**——不按固定列，按文档字段存。

三层：Database → Collection → Document（BSON 键值对）。文档里可以再嵌文档、数组、文档数组。

```js
// 一个玩家 = 一个文档，字段可有可无、文档之间不必一致
{
  "_id": 1,
  "job": "剑士",
  "equipments": ["sword_01", "armor_02"],
  "activities": { "valentine": false, "spring": true },
  "master": { "joined": true, "masterId": 9001 }
}

// 多维查询 + 索引（不是只能 KV）
db.players.find({ job: "剑士", "activities.valentine": false })
db.players.createIndex({ job: 1, "activities.valentine": 1 })
```

`_id` 默认主键，常见类型是 **ObjectId**。

| SQL | MongoDB |
| --- | --- |
| 表 | Collection（集合） |
| 行 | Document（文档） |
| 列 | Field（字段） |
| 主键 | `_id` / ObjectId |
| 嵌套表 | 嵌入式文档 |
| 数组 | 数组 |
| 索引 | 索引 |
| SQL | `find` / `updateOne` / `aggregate` 等 |

* 集合 ≈ 表，文档 ≈ 行。差别在于：文档之间字段可以不一致，不必提前定死 schema
* 集合不用事先建：第一次插入文档或建索引时，不存在就自动创建

### BSON

文档长得像 JSON，实际存 **BSON（Binary JSON）**。在 JSON 上扩展了二进制、时间等类型，落盘和传输更合适当存储格式。

* 大元素带**长度前缀**，扫描、遍历更快，这是选 BSON 的主因
* 长度前缀和显式数组下标会让部分文档比 JSON **更占空间**

键是字符串（UTF-8），注意：

* 不能含 `\0`（表示键结束）
* `.` 和 `$` 有特殊含义，只在特定语法里用
* `_` 开头多半是保留键（如 `_id`）

### 集合名 / 库名

* 集合：不能空、不能含 `\0`、不能以 `system.` 开头（系统集合前缀）、一般以字母或下划线开头且不能含 `$`
* 库名会变成文件系统里的文件：不能空、不能含空格 `. $ / \` 和 `\0`，建议全小写，最长 64 字节

### 几个特殊库

* **admin**：存用户和角色（`system.users` / `system.roles`）。用户在 admin 上有 `dbAdminAnyDatabase`，就继承所有库权限；关服等部分命令只能在这跑。别当业务库用
* **local**：不复制到其它节点/分片，只存本机数据。别当业务库，也难按常规备份恢复
* **config**：分片集群的元数据
* **test**：没指定库时默认连这个

## 特点

* 文档存储 + 模式自由，嵌套结构能少拆表
* 查询不只是 KV：CRUD、聚合、文本搜索、地理空间
* **单文档天生原子**；多文档事务要看版本（见下文）
* BSON 二进制存储；WiredTiger **自带压缩**
* 索引种类多：单字段、复合、多键、哈希、文本、地理位置
* 副本集自动 failover（选主对客户端基本无感）；分片自动路由
* 单文档上限 **16MB**，更大用 **GridFS** 切块存
* `map-reduce`：5.0 起官方不推荐，改用**聚合管道**

## 单机：存储引擎与 WiredTiger

和 MySQL 一样是 **插件式引擎**：Server 层和引擎解耦，建库/建集合时可指定。查询语句最终转成引擎接口：`updateOne` → `update()`，`find` → `search()`。

* 早期默认 **MMAPv1**，**4.x 起不再支持**
* **WiredTiger**：3.2 起默认，新部署用这个。文档级并发、Checkpoint、压缩
* **In-Memory**（企业版）：数据留内存，延迟更可预期，不当磁盘主存储

可以把单机路径记成：文档 → 页 → 树 → 内存 → 日志 → 刷盘。

### 数据页

集合落在 `.wt` 文件上，按 **页（page）** 读写，常见页大小 **32KB**（InnoDB 常见 16KB）。只动相关页，避免整文件 IO。

B+ 树的每个节点就是一页，三种：

* **root page**：根
* **internal page**：中间索引，只存 key
* **leaf page**：真正存 key/value；含页头（类型、载荷大小、记录数）和块头（checksum、磁盘位置）

### B+ 树

默认就是 **B+ 树**：内部节点只 key，叶子 key+value。`_id` 是主键索引，其它字段可以建辅助索引。

多数 NoSQL（HBase、Cassandra、RocksDB）走 LSM。WiredTiger **引擎本身也支持 LSM**，但 MongoDB 用它时默认仍是 B+ 树。网上说「非叶子存完整文档的 B 树」不准确，面试按 **B+ 树 + COW** 答。

**写路径和 InnoDB 不同**：

* InnoDB：沿根到叶短暂加锁，再锁目标行
* WiredTiger：**文档级并发**；几乎不锁原页，**复制新页再写（Copy-on-Write）**，旧页继续对外读，之后再把复制页合并回树

### Cache

同缓冲池：热点数据页放内存 Cache，命中就不读盘；内存不够用 **LRU** 淘汰，尽量只留热点。

### Journal 和 Checkpoint

Journal 就是 **WAL**，角色接近 InnoDB redo：

* 写操作先记 **Journal Buffer**，再改内存里的数据页；Buffer 定时刷到磁盘 Journal 文件
* 进程崩了，重启用 Journal **重做**，尽量不丢
* Journal 是顺序写，脏页落盘是随机写，所以先记日志再改页

内存脏页不能等满了一次刷（太猛），也不能刷太勤（占 IO）。**Checkpoint** 定期把脏页批量刷盘；这个点之前的 Journal 可以丢掉。

以上合在一起就是 WiredTiger。

### 数据压缩

压缩用 CPU 换磁盘。默认：

* 集合：**Snappy 块压缩**（Google，偏速度，大约 3～5 倍）
* 索引：**前缀压缩**

集合还可选：

* **zlib**：压缩比大约 5～7 倍，更吃 CPU
* **zstd**（Zstandard，Facebook）：4.2 起可用，压缩率和 CPU 通常优于 zlib 那档

Journal 默认也 Snappy；记录 **≤128 字节不压**。

## Server 层

角色同 MySQL 的 Server：夹在查询语句和存储引擎中间，两边用接口解耦，所以能换引擎。

* **连接管理**：管客户端连接
* **查询解析器**：语法、字段是否合法
* **查询优化器**：选索引、生成执行计划
* **执行器**：按计划调引擎接口

单机差别主要在数据单元：InnoDB 读写页里的**行列**，WiredTiger 读写页里的**文档**。高性能有了，十亿级还要扩展和高可用。

## 聚合

把多个文档（甚至多个集合）汇总计算：求和、最大、按时间分析。两种用法：

* **聚合管道（首选）**：多阶段流水线，上一阶段的输出当下阶段的输入
* **单一目的方法**：`count()`、`distinct()`、`estimatedDocumentCount()`
* 5.0 起不要再把 **map-reduce** 当首选

和 SQL 大致能对上：`$match` ≈ WHERE，`$project` ≈ SELECT 投影，`$group` ≈ GROUP BY，`$lookup` ≈ 同库 JOIN（能力弱很多）。

```js
db.orders.aggregate([
  { $match: { status: "A" } },                       # 筛选
  { $group: { _id: "$cust_id", total: { $sum: "$amount" } } }  # 按客户汇总金额
])
```

常用阶段：

| 操作符 | 作用 |
| --- | --- |
| `$match` | 筛选 |
| `$project` | 投影：抽字段、改名、算出新字段 |
| `$sort` / `$limit` / `$skip` | 排序、条数、跳过 |
| `$count` | 计数 |
| `$group` | 分组聚合 |
| `$unwind` | 数组拆成多条文档 |
| `$lookup` | 连接同库另一个集合 |

## 事务

NoSQL 常为扩展和性能砍事务，MongoDB 是例外，也谈 ACID。隔离级别：WiredTiger 支持读未提交、读已提交、**快照**；MongoDB 启动默认 **snapshot**。

* **单文档**：写入本身就是原子的。多数业务靠嵌入文档/数组，就能少开跨文档事务
* 说「MongoDB 事务」通常指 **多文档**，比单文档写更贵
  * **4.0**：副本集内的多文档 ACID
  * **4.2**：分片集群也支持；官方把副本集和分片上的多文档事务都叫 **分布式事务**（一个意思）
* 前提（4.2+）：主必须 WiredTiger；从可以是 WiredTiger 或 In-Memory。4.0 只有 WiredTiger 副本集
* **4.4** 起才能在事务里建集合和索引（更早不行）

选型表里「4.0+ 才有多文档事务」指的就是这条时间线，不是「MongoDB 没有事务」。

## 索引

目的同 MySQL：提高查询效率。没索引就 **集合扫描**（扫每个文档）；有合适索引就缩小检查范围，排序也能直接用索引里的顺序。

写要同时改文档和索引，必然拖写入。写多读少、或不在乎读延迟时，别乱建。

### 类型

* **单字段**：建在一个字段上。创建时升/降序无所谓，可以从头或从尾遍历
* **复合索引**：多个字段，也叫联合索引。字段顺序和每个字段的方向都重要
* **多键索引**：字段是数组时，给数组**每个值**建索引项。按数组里的元素当条件查，仍然能走索引
* **哈希索引**：按数据的哈希值索引，给哈希分片用
* **文本索引**：字符串或字符串数组上的全文检索。一个集合只能有一个文本索引，但这个索引可以覆盖多个字段。官方支持，**性能一般，暂不建议当主力搜索**
* **地理位置**：基于经纬度，适合 2D / 3D 位置查询
* **唯一索引**：字段不存重复值。集合里已经有冲突文档时，后台创建会失败
* **TTL 索引**：给文档设过期时间，到期删除。适合日志、会话、机器事件这类只留一段时间的数据

### 复合索引

规则同联合索引：**最左前缀**，排序时方向还要对上。

索引 `{ a: 1, b: 1, c: 1 }` 等于顺带有 `{a}`、`{a,b}`、`{a,b,c}`，**没有**单独的 `{b}`、`{c}`、`{b,c}`。

索引 `{ userid: 1, score: -1 }`：先按 userid 升序，同一 userid 内再按 score 降序。sort 必须和索引完全同向，或整条**整体取反**（从尾巴往回扫）。字段顺序反了，或只把其中一个方向反过来，都走不了这个索引。

```js
# 索引 { userid: 1, score: -1 } 能覆盖
db.s2.find().sort({ userid: 1, score: -1 })
db.s2.find().sort({ userid: -1, score: 1 })   # 整条反过来扫

# 走不了：只翻了一个方向，或字段顺序反了
db.s2.find().sort({ userid: 1, score: 1 })
db.s2.find().sort({ score: -1, userid: 1 })
# 不确定就 explain()
```

### TTL

带 `expireAfterSeconds`，到期删。除了多这个属性，其它和普通索引一样。

* 后台线程读 TTL 字段判断是否过期，**大约每 60 秒**跑一次，不保证立刻删。量大时上次删不完、下次又开始，过期后再拖 60 秒以上都有可能
* 副本集里删除线程**只在 Primary** 跑，从库靠 oplog 同步这条删除
* 限制：只能是单字段；不能复合、不能建在 `_id` 上、不能建在 **Capped Collection**（上限集合不允许删文档）；字段上已经有普通索引，就不能再加 TTL

### 覆盖查询

同覆盖索引：结果只从索引出，不回文档，通常更快。条件是：

* 查询条件里的字段都在索引里
* 返回的字段也都在**同一**条索引里
* 查询里没有字段等于 `null`

Mongo 有个容易漏的点：默认会返回 `_id`。索引里如果没有 `_id`，必须投影 `{ _id: 0 }`，否则还是要回文档。

```js
db.users.createIndex({ gender: 1, user_name: 1 })
db.users.find({ gender: "M" }, { user_name: 1, _id: 0 })
```

## 高可用：副本集 + 分片

副本集解决的问题和 MySQL 主从一样：**挂了还能写、可以从库读**。分片解决的是单机容量和吞吐不够（磁盘、CPU、内存、网卡顶满），类似分库分表 / Redis Cluster，代价是部署和维护更复杂。

分片集群 = 多个 Shard 切数据 + mongos 路由 + Config Server 管元数据。**3.6 起每个 Shard 必须部署成副本集**。

### 副本集

一组维护同一份数据的 `mongod`。客户端连的是整个副本集，不是单台机器。

* **Primary**：整个集群的写入口，变更写入 **oplog**。**默认读也走主**
* **Secondary**：从主拉 oplog 在本地回放。可以配成可读；优先级设成 0 则永远不参选
* **Arbiter（0 或 1 个）**：不存数据，选举时只投票，用来凑多数票。省机器或多机房容灾时用。MySQL 主从没有这个角色

典型三人组：1 主 2 从，或 1 主 1 从 1 仲裁。最多一个主。主挂了自动选新主，规则会偏向**数据最全**的节点，客户端基本无感。

oplog 在 **local** 库，是特殊的 **Capped Collection（上限集合）**：定长循环队列，往尾部追加，满了覆盖最旧文档。顺序写固定空间，IO 快；不建索引更快。主写完追加一条，从不断拉取回放。和 Journal 的分工见上一节。

主压力不大时不必硬做读写分离。**4.0 之前**写可能堵读，除非业务能接受延迟。

### 分片集群

* **Config Servers**：本身也是一个副本集，存分片地址、Chunk 分布等元数据
* **mongos**：不存业务数据，向 Config 拿配置，把请求转到对应分片，再合并结果。客户端**只连 mongos**。请求量大时 mongos 自己也可以横向加
* **Shard**：整体数据的一个子集

### 分片键

文档里的一个字段，决定这条文档落在哪一片。不是随便一个字段都能当片键：

* 所有文档都必须有这个字段
* 必须是集合上的索引：单字段，或复合索引的**左前缀**；不能是多键、文本、地理索引
* 不超过 **512 字节**
* **4.2 之前**片键值不可改。4.2 起除了 `_id` 以外可以改片键值。**5.0** 支持 live resharding，可以换一套片键

选片键尽量多满足下面几条，否则后面迁块会很难看：

* **基数要大**：年龄这种只有几十档，chunk 数量上不去，块会越胀越大，变成迁不走的 **jumbo chunk**
* **值要分布均匀**：少数值占爆某几个块，一样不均、成为热点
* **查询尽量带片键**：mongos 才能直达分片；不带就广播到所有分片再等齐
* **别用纯单调递增/递减**：写全打在最后一片，那一片持续胀、不停迁移

### 分片策略

| | 范围分片 | 哈希分片 |
| --- | --- | --- |
| 怎么切 | 按片键值的区间切成 Chunk | 先算单字段哈希，再按哈希区间切 |
| 优点 | mongos 容易定位，范围查询友好 | 写能打散，各片更匀 |
| 缺点 | 容易热点，写不散 | 范围查询要扫所有分片 |
| 适合 | 非单调、基数大、重复少、要范围查 | 单调递增、要随机写、读也比较随机 |

还可以配 **复合片键**，例如一个低基数字段加上一个单调递增字段。

### Chunk 与均衡

集群不记「每一条文档在哪台机器」，只记 **Chunk 在哪片、这段片键覆盖哪些数据**。Chunk 是一组文档组成的逻辑块，区间互不相交，并集是全量数据。

* 默认一块上限 **64MB**（可调 1～1024MB，没特殊需求保持默认）
* 插入、更新让块超限 → mongos 感知后做 **Chunk 分裂**
* 各片上的 Chunk **数量**不均 → **Balancer** 做 **Rebalance**（默认开）。Balancer 从 **3.4** 起跑在 **Config Server 的 Primary** 上，数量到阈值就迁块
* Chunk **只分裂不合并**。把 chunkSize 调大，也不会自动把小块合回去
* Rebalance 比较吃资源：放到业务低峰、提前预分片、或设时间窗

### 读写走一遍（分片集群）

1. 客户端连 mongos
2. mongos 用缓存的分片信息定位（必要时向 Config Server 刷新）
3. 转发到对应分片的副本集（一次请求可能打到多片）
4. 分片内部：解析 → 优化器选索引 → 执行器调 WiredTiger
   * **读**：先看 Cache，没有再读盘加载进 Cache；mongos 收集各片结果，合并、排序后回客户端
   * **写**：记 Journal，COW 出新页；Checkpoint 把脏页刷盘；主把数据同步给从。**主和足够多的从都确认**后，分片才回 mongos；相关分片都确认了，mongos 才对客户端说成功
